
> 基於 2026-03-26 架構討論，針對 ETL Pipeline 三個核心挑戰的結構性收斂。
> 本文件聚焦於「存儲層的合法操作邊界」這個統一問題，從第一性原理推導出 ETL 層在概念抽取、認識論事件標註、模糊去重三個領域的精確職責。

## 討論脈絡

### 起點：ETL Pipeline 的挑戰識別

進入 Pipeline 實作前，識別出五個按「越早阻塞越多下游決策」排序的核心挑戰：

1. 概念抽取的粒度問題
2. 認識論事件的偵測複雜度
3. 跨對話的模糊去重
4. 增量處理 vs 全量重建的取捨
5. Context window 壓力下的 prompt 設計

討論過程中發現 #1、#2、#3 背後是同一個結構性問題：

> **存儲層需要結構才能運作，但系統哲學要求語意在推理時湧現。ETL 層預先固化多少判斷？留白多少空間？**

三個領域分別展開後，收斂到同一條原則。

### 推導路徑

```
概念抽取的粒度問題
  → 概念節點的存在理由是什麼？（第一性原理）
  → 消去法：不抽取 → Kuzu 失去意義；過度抽取 → 違反原則七
  → 結論：概念節點的職責僅是「可遍歷的拓撲骨架」
  → 承認「正確粒度」無先驗答案，只能從 POC 迭代中校準

認識論事件的偵測
  → 七種事件類型是否合法？（用系統自己的哲學反問自己）
  → top-down 的離散分類 vs 類比的認知過程 → 非法
  → 回到認知科學第一性原理 → 收斂到量變 vs 質變的根本區分
  → 擴展為三個正交的三值維度
  → confidence 浮點數的矛盾 → null 吸收不確定性

模糊去重
  → 風險不對稱性（漏合可逆，錯合不可逆）
  → 別名表的隱藏問題（top-down 語意判斷的偽裝）
  → 社群結構作為軟去重的自然湧現
  → 去重步驟被消除，成為社群偵測的副產品
```

## 修訂十三：概念抽取的職責定位——拓撲骨架，非知識表徵

### 原文問題

原始架構文件未定義概念抽取的粒度標準。先前討論中的「粗 vs 中 vs 細」框架暗示存在一個可先驗決定的正確粒度。

### 修正

透過兩個極端的消去法確立概念節點的精確職責：

> **概念節點的存在理由是且僅是：提供 Kuzu 可遍歷的拓撲骨架。**

- 概念節點不是知識的表徵，不需要「正確地」捕捉所有語意細節
- 它只需要提供足夠的結構，讓圖能做**只有圖才能做的事**：多跳遍歷、社群偵測、Session 邊集合身份、Self 節點認知側寫
- 抽取目標從「抽取所有重要概念及其關係」轉移為「辨識足以標記主題座標的錨點概念」

### 粒度的校準方法

承認「正確粒度」不存在先驗答案。粒度的「正確性」只能在下游被評估——在社群偵測與視覺化完成後，由人工判斷「這個圖有沒有用」。

POC 的核心迴圈即為粒度校準機制：

```
prompt 設計 → 抽取 → 去重 → 建圖 → 社群偵測 → 視覺化
     ↑                                              │
     └──────── 人工判斷：「這個圖有沒有用？」 ─────────┘
```

啟動策略：

```
第一輪：zero-shot prompt → 對 5-10 個熟悉的對話跑完整 pipeline
        → 人工判斷抽取結果 → 手動校正為 golden examples
第二輪：few-shot（用 golden examples）→ 跑更大範圍 → 再校正
第三輪：穩定的 prompt + few-shot → 跑全量
```

Few-shot examples 不是憑空設計的，而是從人工對具體語料的判斷中長出來的。粒度的「正確性」被嵌入在 examples 裡，而非抽象的 prompt 指令中。

### 評估標準

Stage 6 視覺化時的具體評估問題：

- 社群是否對應到認知中真實存在的主題區域？
- Session 之間的共享概念是否反映出真實的跨對話連結？
- 圖上是否存在自己沒意識到的連結，且它是有意義的而非噪音？

### 新增設計原則

> **原則十三（新增）：概念節點的職責是拓撲骨架，不是知識表徵**
>
> 概念抽取的目標是辨識足以導航的錨點，不是完整表徵語意。正確粒度無先驗答案，從 POC 迭代中校準。

### 影響段落

原始架構文件 §6 Session 節點相關段落需補充概念節點的職責定義。

## 修訂十四：認識論事件從七種離散分類重構為三個正交的三值維度

### 原文問題

原始架構文件 §7 定義七種認識論事件類型（ConceptElaborated、ViewShifted、ConceptFissioned、ConceptMerged、RelationInverted、ContradictionFlagged、ContradictionResolved）。

這個設計存在根本性的合法性問題：用離散的數位分類精確重現類比的認知過程，本質上是 top-down 的強制詮釋——與修訂十一確立的原則（wikilinks 語意不被 ETL 預先詮釋）直接矛盾。如果連人類明確寫下的 wikilinks 都不允許被 ETL 機械式詮釋，那對認知漂變的七分類更不應該在存儲層固化。

### 認知科學的收斂

回到認知科學的第一性原理，幾十年的研究在認知變化的根本分類上收斂到一個核心區分：

- **Piaget（1950s）**：同化（Assimilation）vs 調適（Accommodation）
- **Rumelhart & Norman（1978）**：增積 / 調校 / 重組（三層細化）
- **Chi（2008）**：豐富化（Enrichment）vs 修訂（Revision）

所有模型指向同一根本軸：**結構不變（量變）vs 結構改變（質變）。**

判斷「有沒有」（質）遠比量化指數（量）更容易且更合理——這是二分判斷對 4B 模型而言可靠可執行的根本理由。

### 修正：三個正交的三值維度

在量變/質變的基礎上，識別出三個正交的二元維度：

```
維度                    語意                              偵測信號
──────────────────────────────────────────────────────────────────────
structural_change      結構有沒有變                       同一概念在不同 Session 中的
                       量變 vs 質變                       框架定位是否改變

tension                有沒有產生未解決的矛盾             「但是我之前以為」「這跟之前
                       收斂 vs 發散                       矛盾」vs「原來如此」「說得通了」

integration            概念之間變得更統一還是更分化         「X 和 Y 其實是同一件事」
                       合流 vs 分岔                        vs「X 裡面其實有兩個不同機制」
```

每個維度採**三值邏輯**：

```
True  = 模型有足夠證據判斷為是
False = 模型有足夠證據判斷為否
Null  = 證據不足以做判斷，或維度不適用
```

### Null 作為 confidence 的替代

引入 confidence 浮點數會產生根本矛盾——在一個質性判斷上疊加量化指標，等於跌回「用數位量化類比過程」的陷阱。而且 4B 模型輸出的 confidence 數值本身不可靠。

Null 吸收了「不適用」與「不確定」兩種情況。模型的信心程度被編碼進「敢不敢 commit 一個 true / false」這個決策本身。不確定時標 null，比「標 true 然後附上 confidence = 0.4」更誠實。

區分「不適用」與「不確定」本身也是語意判斷——要求 4B 模型不只判斷維度的值，還要判斷維度的適用性，會把 prompt 複雜度翻倍。兩者在下游效果一致（物化程序遇到 null 跳過該維度），精細區分留給查詢時 LLM 自行從上下文判斷。

### 有效組合與原始事件類型的對照

三個三值維度理論上有 27 種組合（含 null）。全非 null 的有效組合為 8 種：

```
structural  tension  integration  自然對應的認知現象（查詢時湧現，非 ETL 標註）
─────────────────────────────────────────────────────────────────────────────
false       false    true         日常學習：知道更多了，東西串起來了
false       false    false        區分深化：同框架內看到更多細節
false       true     true         疑惑浮現：東西看似該連但連不上
false       true     false        細節矛盾：具體事實之間打架
true        false    true         頓悟合併：框架重組，多歸一
true        false    false        框架分裂：一個概念拆開了，各自獨立
true        true     true         深層矛盾：根本框架之間的衝突
true        true     false        範式危機：舊框架碎了，新框架還沒成形
```

右欄的詮釋不是 ETL 的產出——它在查詢時由 LLM 根據 flags 組合與上下文片段自行湧現。

與原始七種事件的對照：

```
原始事件類型              最接近的組合
──────────────────────────────────────────
ConceptElaborated       (false, false, *)
ViewShifted             (true, false, *)
ConceptFissioned        (true, false, false)
ConceptMerged           (true, false, true)
ContradictionFlagged    (*, true, *)
ContradictionResolved   tension 從 true → false 的轉移
RelationInverted        (true, false, *) 的特例
```

七種事件大致被覆蓋，但產生方式根本不同——不是先定義類別再歸類，而是從正交維度的組合中 bottom-up 湧現。某些組合（如 `true, true, true`）在原始分類中不存在，但在認知現實中是存在的。

### Event Log Schema 的修正

```
每個認知事件的存儲結構：
{
  concept: "...",
  sessions: [session_A, session_B],
  context_A: "...",              // 前一次提及的上下文片段
  context_B: "...",              // 後一次提及的上下文片段
  structural_change: true | false | null,
  tension: true | false | null,
  integration: true | false | null
}
```

三個維度，三值邏輯，無浮點數。上下文片段保留為 payload，供查詢時 LLM 做精細詮釋。

### 新增設計原則

> **原則十四（新增）：認識論事件以正交的三值維度標註，不做離散分類**
>
> ETL 層對認知事件做三個獨立的三值判斷（structural_change、tension、integration），不試圖將其歸入預定義的事件類型。事件的精細詮釋（這個組合在此脈絡中具體意味著什麼）由查詢時 LLM 從 flags 組合與上下文片段中湧現。

### 影響段落

原始架構文件 §7「認識論事件類型」整節重寫。七種事件類型表被上述三值維度模型取代。

## 修訂十五：模糊去重從獨立步驟消除，成為社群偵測的副產品

### 原文問題

概念去重面臨兩個交織的難題：

1. **風險不對稱**：漏合（同一概念有兩個節點）是可逆的，錯合（兩個不同概念被合成一個）幾乎不可逆且汙染所有下游邊。
2. **灰色地帶的處理**：字串正規化覆蓋表面形式差異，但語意等價的判斷（"attention mechanism" vs "self-attention"）需要上下文相關的語意判斷，屬於 ETL 層的非法操作。

### 別名表的問題

手動維護的別名表（`aliases.yaml`）表面上符合 SSOT B 延伸的哲學，但存在隱藏問題：

- 它要求使用者**預先知道**哪些東西是同一個東西——本質上是 top-down 的語意判斷
- 每次抽取 prompt 粒度調整後，概念表面形式可能改變，別名表需要同步更新
- 維護成本隨語料規模線性增長

### 修正：社群結構作為軟去重

如果兩個名稱真的指向同一個概念，它們會反覆出現在相同的 Session 群裡。這個共現信號是純粹的結構性事實，不需要語意判斷——DuckDB 可以直接從共現矩陣計算。

錯誤的模糊關聯會被統計量自然沖淡：偶然的單次共現在大量真實共現信號中消失。這不是靠精確判斷消除錯誤，而是靠統計量壓低噪音。

去重不再是獨立步驟，而是社群偵測的副產品：

```
原本的流程：
  概念抽取 → 去重（獨立步驟）→ 建圖 → 社群偵測

修正後的流程：
  概念抽取 → 字串正規化（僅此）→ 建圖（帶重複）→ 社群偵測
                                                      ↓
                                              社群結構即軟去重結果
```

### 碎片化風險的評估

不積極去重可能導致拓撲碎片化的擔憂在實際語境下影響輕微：

- 重要概念會在多個 Session 中被提及，即使有兩個節點，兩者的鄰域高度重疊
- Kuzu 做多跳遍歷時，從任一節點出發到達的 Session 集合大致相同
- 只被提過一兩次且每次用不同名稱的概念，pkm_score 本來就低，可能不會通過物化閾值進入 GraphDB

### ETL 去重層的最終範圍

```
ETL 去重：
  1. 字串正規化（大小寫、空格、標點）
  2. 完全相同的正規化結果 → 合併

  到此為止。不做 embedding 相似度比對，不做 LLM 判斷，不維護別名表。
```

灰色地帶的處理完全交由社群偵測的結構性湧現。查詢時 LLM 看到同一社群裡的疑似重複節點，自然理解它們的等價關係。

### 新增設計原則

> **原則十五（新增）：模糊去重不在 ETL 層執行，由社群結構的湧現取代**
>
> ETL 層只做確定性的字串正規化。語意等價的判斷不在存儲層固化——疑似重複的概念保留為獨立節點，透過社群偵測的共現模式自然呈現等價關係。寧可漏合（可逆），不可錯合（不可逆）。

### 影響段落

POC Stage 3（模糊去重）的範圍大幅縮減為純字串正規化。原始架構文件中未展開的 ETL Pipeline 細節需反映此修正。

## 統一結論：ETL 層的合法操作邊界

三個領域的修訂收斂到同一條原則：

> **ETL 層只做「結構性的最小判斷」——剛好足以讓下游工具運作，但不多一步進入語意詮釋的領域。**

| 合法（ETL 該做的） | 非法（ETL 不該做的） |
|---|---|
| 辨識概念錨點（讓 Kuzu 有節點可遍歷） | 完整表徵概念的語意與關係 |
| 三值的二元維度標註（讓物化程序有最低限度的信號） | 精確分類認知事件的類型 |
| 存儲兩端上下文片段（讓 LLM 在查詢時有素材） | 預先詮釋上下文片段的語意 |
| 字串正規化（讓同一表面形式不重複） | 語意等價判斷（embedding 比對、LLM 合併） |
| 保留疑似重複為獨立節點 | 積極合併灰色地帶的概念 |

**這條邊界就是結構與靈活性的和解點。** 存儲層的結構量被壓到「必要最小」，靈活性的空間被最大化保留。存儲層提供骨架，推理層賦予血肉。
