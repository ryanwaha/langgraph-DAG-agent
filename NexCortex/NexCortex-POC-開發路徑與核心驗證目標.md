## POC 的定位

### POC 不是什麼

POC 不是系統的縮小版。它不涉及 Kuzu、Event Log、敘事層、向量索引、Agent 工具箱。這些組件的設計已在架構層收斂，不需要 POC 驗證。

### POC 驗證的核心假設

整個系統架構的可行性最終取決於一個尚無經驗證據的假設：

> **從對話紀錄中，可以透過 LLM 抽取出足以構成有意義拓撲骨架的概念錨點。**

「有意義」的定義：社群偵測產出的社群結構，對應到認知中真實存在的主題區域，且圖中存在非顯而易見的跨主題連結。

如果這個假設不成立——抽出的概念要麼太碎（噪音淹沒信號）、要麼太粗（拓撲退化為幾個巨大的連通分量）——後續所有組件都不值得建構。

### POC 的終止條件

**成功**：經過 ≤ 3 輪 prompt 迭代，Stage 6 的視覺化結果通過人工評估（見下方評估標準）。

**失敗**：3 輪迭代後仍無法產出有意義的社群結構。此時需要重新評估的不是 prompt，而是概念抽取本身的可行性——可能需要更大的本地模型、不同的抽取粒度策略、或對 SSOT A 的前處理方式做根本調整。

## 開發路徑

### 修訂後的 Pipeline 結構

```
Stage 1 ─► Stage 2 ─► Stage 3 ─► Stage 4 ─► Stage 5 ─► Stage 6
 JSONL      概念        字串       共現圖      社群        視覺化
 解析       抽取        正規化     建構        偵測        + 評估
                ▲                                           │
                └──── prompt 迭代迴圈（核心瓶頸）─────────────┘
```

### Stage 間的依賴與資料流

```
Stage 1 輸出：List[Session] — 每個 Session 含 id、sum_text、metadata
Stage 2 輸出：List[(session_id, concept_label)] — 每個 Session 的概念清單
Stage 3 輸出：同上，concept_label 經正規化
Stage 4 輸出：共現矩陣（DuckDB / Parquet）+ networkx 圖物件
Stage 5 輸出：社群分配（每個概念所屬社群）+ 模組度指標
Stage 6 輸出：pyvis 互動式視覺化 + 評估紀錄
```

## 各 Stage 詳細規格

### Stage 1：JSONL 解析

**工具**：`dag_engine.load()`（現有）

**輸入**：SSOT A 的 JSONL 對話檔案（5-10 個熟悉的對話，首輪）

**輸出**：Session 物件清單，每個包含 `id`、`sum_text`、`parents`

**驗證**：`sum_text` 非空、長度分佈合理、覆蓋足夠的主題多樣性

**預期阻力**：接近零。唯一風險是 `sum_text` 品質不一致（過短、過於通用），需在此階段發現並記錄。

**決策點**：如果 `sum_text` 品質普遍不足以支撐概念抽取，需考慮改用原始 `q` + `a` 欄位做抽取輸入，代價是 context window 壓力上升。

---

### Stage 2：概念抽取（核心瓶頸）

**工具**：Qwen 3.5 4B（本地推理）

**輸入**：單個 Session 的 `sum_text`

**輸出**：該 Session 中出現的概念標籤清單（字串列表）

**抽取目標**（修訂十三）：辨識足以標記主題座標的錨點概念。不是知識表徵，是拓撲骨架。

**Prompt 迭代策略**：

```
第一輪：zero-shot
  → 對 5-10 個熟悉對話的 sum_text 跑抽取
  → 人工逐一審閱抽取結果
  → 標記：遺漏的重要概念、不應出現的噪音概念、粒度偏差方向
  → 手動校正為 golden examples

第二輪：few-shot（使用 golden examples）
  → 擴大到 20-30 個對話
  → 對比 zero-shot 結果，評估 few-shot 的改善幅度
  → 更新 golden examples

第三輪：穩定的 prompt + few-shot
  → 跑全量語料
  → 抽樣檢查新語料的抽取品質
```

**Prompt 設計的約束條件**：

- Qwen 4B 的 context window 限制（需實測 `sum_text` 的典型 token 數 + prompt + few-shot examples 的總量）
- 輸出格式：JSON 列表，每個元素為字串。不要求結構化的 (concept, relation, concept) 三元組——關係由 Stage 4 的共現自然產生
- 語言：`sum_text` 的語言（可能混合中英文），概念標籤統一為英文（或依語料主語言決定，首輪實測後確定）

**評估指標**（人工，非自動化）：

| 指標 | 判斷方法 |
|------|----------|
| 覆蓋率 | 閱讀 sum_text，列出自己認為的關鍵概念，對比抽取結果的覆蓋比例 |
| 精確率 | 抽取結果中有多少是噪音（過於泛化、不相關、或純粹是動詞/形容詞而非概念） |
| 粒度一致性 | 同一層次的概念是否保持相似的抽象程度（非嚴格量化，人工判斷） |
| 跨 Session 可比性 | 同一個概念在不同 Session 中是否被抽取為相同或相近的標籤 |

**決策閘門**：Stage 2 的人工評估必須在以下三項上達到「可接受」才進入 Stage 3：
1. 覆蓋率：關鍵概念的大多數被捕獲（允許遺漏邊緣概念）
2. 精確率：噪音概念不超過抽取結果的 ~30%（字串正規化後可進一步壓低）
3. 跨 Session 可比性：同一概念的標籤形式差異在字串正規化可處理的範圍內

---

### Stage 3：字串正規化

**工具**：Python（純函數，無 LLM）

**輸入**：Stage 2 的概念標籤清單

**操作範圍**（修訂十五）：

```
合法操作：
  - 大小寫統一（全部 lowercase）
  - 空格/標點正規化（multiple spaces → single, 去除尾部標點）
  - 完全相同的正規化結果 → 合併

非法操作（不做）：
  - Embedding 相似度比對
  - LLM 語意等價判斷
  - 別名表維護
```

**輸出**：正規化後的 (session_id, normalized_concept) 對照表

**預期阻力**：極低。這是純確定性的字串處理。

**驗證**：正規化前後的唯一概念數量對比（預期下降 10-20%，如果下降不足 5% 說明抽取已經足夠一致，如果下降超過 40% 說明抽取的表面形式變異過大）。

---

### Stage 4：共現圖建構

**工具**：DuckDB（共現矩陣計算）+ networkx（圖物件）

**輸入**：Stage 3 的 (session_id, normalized_concept) 表

**邏輯**：

```
共現定義：兩個概念出現在同一個 Session 中 → 共現一次
邊權重：共現次數
節點：唯一概念
```

**實作路徑**：

```sql
-- DuckDB: 建構共現矩陣
SELECT a.concept AS concept_a, b.concept AS concept_b, COUNT(*) AS weight
FROM concepts a
JOIN concepts b ON a.session_id = b.session_id AND a.concept < b.concept
GROUP BY a.concept, b.concept
```

**輸出**：networkx.Graph 物件 + 共現矩陣 Parquet

**驗證**：
- 圖的基本統計：節點數、邊數、平均度、最大連通分量佔比
- 如果最大連通分量佔比 > 95%，圖可能過度連通（抽取粒度太粗或概念太泛化）
- 如果孤立節點佔比 > 30%，可能抽取的概念太具體或語料覆蓋不足

**決策閘門**：圖的連通性在合理範圍（最大連通分量 50-90%，無單一概念連結全圖）。

---

### Stage 5：社群偵測

**工具**：networkx + community（Louvain 演算法）

**輸入**：Stage 4 的 networkx.Graph

**參數**：Louvain `resolution`（預設 1.0，需要校準）

**校準策略**：

```
resolution < 1.0 → 較少、較大的社群（粗粒度分群）
resolution = 1.0 → 預設行為
resolution > 1.0 → 較多、較小的社群（細粒度分群）

校準方法：
  1. 先用 resolution = 1.0 跑一次
  2. 檢查社群數量與大小分佈
  3. 如果社群太少（< 5）→ 增加 resolution
  4. 如果社群太多（> 30）且大量單元素社群 → 降低 resolution
  5. 目標：社群數量 8-20，每個社群 3-15 個概念（大致範圍，非硬性約束）
```

**輸出**：每個概念的社群分配 + 模組度分數（modularity）

**模組度的解讀**：
- Q > 0.3：存在有意義的社群結構
- Q < 0.1：社群結構接近隨機，可能圖過度連通或概念粒度有問題
- 模組度本身不是終極評估——高模組度但社群語意不對應認知現實，仍然是失敗

**驗證**：模組度 > 0.2 且社群大小分佈合理（無佔全圖 50%+ 的超級社群）。

**軟去重的附帶觀察**（修訂十五）：檢查同一社群內是否存在疑似重複的概念。這不是 Stage 5 的正式輸出，但可作為抽取品質的信號：如果大量疑似重複出現在同一社群，說明抽取的表面形式一致性仍有改善空間。

---

### Stage 6：視覺化與評估

**工具**：pyvis

**輸入**：Stage 4 的圖 + Stage 5 的社群分配

**視覺化規格**：
- 節點顏色：按社群分配著色
- 節點大小：按度（degree）或出現頻次
- 邊粗細：按共現權重
- 互動功能：hover 顯示概念名稱、所屬社群、連結的 Session 數量

**核心評估問題**（人工判斷，無法自動化）：

| #   | 問題                            | 通過條件                   |
| --- | ----------------------------- | ---------------------- |
| E1  | 社群是否對應到認知中真實存在的主題區域？          | 至少 70% 的社群可以被命名為有意義的主題 |
| E2  | Session 之間的共享概念是否反映出真實的跨對話連結？ | 抽樣 5-10 條高權重邊，確認連結合理   |
| E3  | 圖上是否存在自己沒意識到的連結，且是有意義的（非噪音）？  | 至少發現 1-2 個有價值的非預期連結    |
| E4  | 圖的整體結構是否「看起來對」？               | 主觀判斷，但需要能用一句話描述圖的整體故事  |

**評估紀錄格式**：

```markdown
## POC 評估紀錄 — 迭代 #N

日期：
語料範圍：N 個對話檔案，M 個 Session
Prompt 版本：zero-shot / few-shot vN

### 圖統計
- 節點數：
- 邊數：
- 社群數：
- 模組度：
- 最大連通分量佔比：

### E1 社群語意評估
| 社群 | 主要概念 | 命名 | 合理性 |
|------|----------|------|--------|

### E2 跨對話連結抽樣
| 概念 A | 概念 B | 權重 | 合理性 |
|--------|--------|------|--------|

### E3 非預期發現

### E4 整體判斷

### 下一步
- [ ] prompt 調整方向：
- [ ] 粒度調整方向：
```

## 技術預備事項

### 執行前需確認

| 項目 | 確認內容 |
|------|----------|
| Qwen 4B 推理環境 | 本地部署就緒、推理速度可接受（目標 < 5s / session） |
| `dag_engine` | `load()` 能正常解析目標語料、`sum_text` 欄位存在且非空 |
| DuckDB | Python binding 可用、可直接查詢 Parquet |
| networkx + community | `pip install python-louvain` 可用 |
| pyvis | 安裝可用、可輸出互動式 HTML |
| 語料選擇 | 5-10 個主題多樣、你熟悉內容的對話檔案已選定 |

### 預估工作量分佈

```
Stage 1：0.5 天（現有工具，僅需驗證 sum_text 品質）
Stage 2：2-4 天（prompt 設計 + 迭代，核心瓶頸）
Stage 3：0.5 天（純字串處理）
Stage 4：0.5 天（SQL + networkx）
Stage 5：0.5 天（Louvain + 參數校準）
Stage 6：1 天（pyvis + 人工評估 + 紀錄）

單輪迭代：5-7 天
含 2-3 輪迭代：10-20 天
```

## POC 成功後的銜接

POC 驗證的是概念抽取與社群結構的可行性。成功後，下一階段的優先順序：

```
1. Kuzu 整合（將共現圖從 networkx 遷移到 Kuzu，加入 Session 節點）
2. 全量語料處理（擴展到完整 SSOT A）
3. 認識論事件偵測的獨立迭代（三值維度模型，依賴穩定的概念抽取）
4. Event Log 建立（DuckDB + Parquet）
5. 向量索引建立
6. 敘事層 / LCM DAG
```

認識論事件偵測被刻意排除在 POC 關鍵路徑之外（修訂說明 03），因為它依賴穩定的概念抽取結果，且三值維度模型需要跨 Session 的比較上下文——這在 POC 的小規模語料上難以有意義地測試。
