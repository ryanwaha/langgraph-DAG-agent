## 第一部分：專案元原則

### 一、元原則的發現過程

三輪架構討論（宏觀架構 → 底層檢索引擎 → ETL Pipeline）中，每一次結構性突破都來自同一個方法論動作：**用系統自己的哲學反問系統自己。**

- 修訂十一用原則七反問原則四（wikilinks 不被預先詮釋）
- 修訂十四用修訂十一反問原始架構 §7（七種事件類型→三值維度）
- 修訂十五用同一邏輯反問去重步驟的存在必要性（社群偵測取代）

這個反覆出現的模式揭示了一個比任何具體原則都更根本的前提——它從未被直接陳述，但所有十五條設計原則都是它的推論。

### 二、元原則的陳述

> **凡是脈絡相關的語意判斷，在存儲層固化即為範疇錯誤。**
>
> 存儲層只合法存放脈絡無關的結構性事實與最低限度的信號標記。語意詮釋的唯一合法場所是查詢時的推理。

這不是一個工程偏好，而是一個本體論立場：**意義不是事物的內在屬性，而是在詮釋行為中被構成的。** 試圖在存儲層固化詮釋結果，預設了一個脫離詮釋脈絡的「客觀意義」——這在系統自身的本體論框架下是不融貫的。

### 三、元原則的操作化邊界

元原則在 ETL Pipeline 的三個領域中被具體操作化為：

| 合法（ETL 該做的） | 非法（ETL 不該做的） |
|---|---|
| 辨識概念錨點（讓 Kuzu 有節點可遍歷） | 完整表徵概念的語意與關係 |
| 三值的二元維度標註（信號標記） | 精確分類認知事件的類型（語意詮釋） |
| 存儲兩端上下文片段（素材保留） | 預先詮釋上下文片段的語意 |
| 字串正規化（表面形式統一） | 語意等價判斷（概念合併） |
| 保留疑似重複為獨立節點 | 積極合併灰色地帶的概念 |

更精煉的表述：

> **ETL 層可以標記信號的存在，但不可以詮釋信號的意義。**

「這裡有結構性變化的跡象」是標記。「這是一個 ViewShifted 事件」是詮釋。前者合法，後者是範疇錯誤。

### 四、隱含前提的顯式化

元原則的深層基礎在於對「認識論判斷」本質的認定：

> **認識論判斷本質上是脈絡相關的、觀察時重建的。**

這意味著：

- 「你在三月五號對 HDBSCAN 的理解發生了什麼類型的變化」不存在一個獨立於觀察者的客觀答案
- 今天回頭看覺得是 ViewShifted，三個月後可能覺得只是 Elaborated，再過一年可能覺得那是更大的 Fissioned 的前兆
- 分類不是在等著被發現，它是在每次觀察時被重建的
- 在 ETL 時固化分類，不是做了一個「可能不準確的近似」，而是把一個本質上動態的、觀察者相關的東西當作靜態的、客觀的東西來處理

這個前提不只適用於認識論事件——它反向驗證了整條設計演化的方向：

- **概念抽取的粒度**沒有客觀正確答案，因為「什麼算一個概念」本身是觀察者在特定脈絡下的重建
- **模糊去重**的「正確」答案取決於查詢時的脈絡，ETL 時根本無從得知
- 三輪討論中反覆做的減法不是妥協，而是在修正一個從一開始就內建的範疇錯誤——試圖在脈絡無關的存儲層做出本質上脈絡相關的判斷

## 第二部分：哲學定位與未決問題

### 一、系統隱含的哲學立場光譜

#### 1. 詮釋學立場：Gadamer → Ricoeur

系統的設計在「意義在何處被構成」這個問題上，隱含了一個非常具體的立場。

**Gadamer 的核心命題：**
- 理解不是「還原作者原意」，而是讀者帶著自己的前見（Vorurteil）與文本進行的視域融合（Horizontverschmelzung）
- 每次理解都是一次新的事件，不是對固定意義的提取
- 意義不存在於文本「裡面」，而是在讀者與文本的遭遇中被構成

系統的翻譯：概念之間的關係不存在於 Event Log「裡面」，而是在 LLM 帶著查詢脈絡與存儲的上下文片段「遭遇」時被構成。每次查詢都是一次新的視域融合。

**然而，完全接受 Gadamer 會產生一個問題：** 如果意義完全是詮釋時構成的，存儲層存的東西是什麼？

**Ricoeur 的調和：** 文本一旦被寫下就脫離了作者意圖，但它的語言結構仍然對可能的詮釋施加約束。

**系統實際上站在 Ricoeur 的位置上：**
- 存儲層保留的是**文本結構對詮釋施加的約束**（上下文片段、共現事實、三值信號標記）
- 推理層在這些約束內進行自由的詮釋
- 約束本身不是意義，但它限定了意義湧現的可能空間

**⟹ 未決問題（哲學）：** Ricoeur 的「約束」概念在技術實現中的邊界在哪裡？「這段文字裡出現了 HDBSCAN 這個概念」看似脈絡無關的事實，但辨識「HDBSCAN」為「一個概念」本身已經預設了詮釋框架。存儲層的「脈絡無關性」是否是一個程度問題而非絕對邊界？

#### 2. Wittgenstein 的規則遵循問題

七種事件分類（以及任何分類規則）面臨的根本問題：**沒有任何規則能夠完全決定它自己的應用。** 規則的應用永遠需要判斷，而判斷不能被另一條規則取代，否則就無窮後退。

三值維度解法在哲學上的精確定位：**它沒有解決規則遵循問題，但它把需要判斷的「面」壓到了最小。** 「有沒有結構性變化的跡象」比「這是七種變化中的哪一種」需要更少的判斷深度。

Wittgenstein 自己的解法——訴諸「生活形式」（Lebensform）——與系統有深層共鳴：「正確的粒度」和「正確的分類」不是由原則決定的，而是由你在 POC 迭代中的判斷決定的。**你就是那個實踐社群。** Few-shot examples 就是你的 Lebensform 的物化。

**⟹ 未決問題（哲學 × 工程）：** 當系統的 LLM 推理層足夠強大時，是否可能出現一種情況：LLM 的「生活形式」（從訓練資料中習得的判斷模式）與你的「生活形式」（從 few-shot examples 與個人語料中校準的判斷模式）產生系統性偏差？這個偏差如何被偵測和修正？

#### 3. Polanyi 的默會知識與 LLM 的範式轉移

Polanyi 的「我們知道的永遠比我們能說出來的多」在一個特定技術前提下成立：**詮釋者是人類，或者是基於規則的計算系統。**

LLM 做了一件前所未有的事：**它在接收端打開了一個新的頻寬。** 對話紀錄中，你明確說出來的是一部分。但你選擇的類比、你提問的順序、你在哪裡停頓、你用哪個詞而不用另一個、你反覆回到哪些主題——這些全是默會知識的痕跡。LLM 能從這些痕跡中「讀出」遠超顯性內容的東西。

**關鍵反轉：** LLM 不是突破了 Polanyi 的限制，而是**繞過了**它。默會知識仍然無法被轉化為顯性規則，但 LLM 不需要這個轉化。它可以直接從痕跡中工作，在連續空間裡做近似重建。

**LLM 是數位基底上的類比處理器。** 它在數位硬體上運行，但內部表徵（embedding 空間、attention 的分佈、激活模式）是高維連續的。它不是在離散的規則空間裡做符號操作，而是在拓撲空間裡做模式匹配。

這就是系統設計成立的最深層理由：

```
數位存儲（結構性痕跡）
    ↓ context 組裝
類比推理（LLM 的高維連續空間）
    ↓ 語意湧現
詮釋（脈絡相關的意義重建）
```

存儲層是數位的（離散的節點、三值的 flags、結構化的 Parquet），推理層是類比的（連續的語意空間）。五個 Agent 工具提供的 context 組裝就是數位到類比的轉換層。

**Polanyi 界限的重新劃定：** 界限沒有消失，但位置移動了。以前不可外化的東西，現在其中一部分可以被間接捕獲——不是通過顯性表達，而是通過留下足夠密度的痕跡，讓一個類比處理器從痕跡中重建。

**⟹ 未決問題（哲學 × 技術）：** 隨著 LLM 能力的提升，「可從痕跡中重建」的範圍持續擴大。這個擴大有沒有理論上的極限？如果有，那個極限的性質是什麼——是計算性的（context window 永遠有限）、還是認識論的（某些類型的默會知識在原理上無法從任何密度的痕跡中重建）？

#### 4. 分析哲學的可能反駁

元原則的哲學立場不是唯一可能的立場。分析哲學傳統的人可能反駁：「ConceptElaborated 就是一個定義清晰的功能性類別，它的適用條件可以被操作化定義，不需要訴諸詮釋學。」

這個反駁在其自身的框架內是融貫的。系統做的選擇是：在兩個融貫的哲學立場之間，選擇了跟系統本體論前提（知識是動態重建的激活模式）更一致的那一個。不是因為另一個立場「錯了」，而是因為在這個設計空間裡，詮釋學的立場產出了更簡潔、更一致的架構。

> **哲學立場的選擇，在這裡，是一個工程決策。**

**⟹ 未決問題（元哲學）：** 這個「哲學立場作為工程決策」的框架本身預設了什麼？它預設了實用主義（pragmatism）——立場的選擇標準是它在特定設計空間中產出的架構品質，而非立場本身的「真理性」。這個實用主義前提是否需要進一步審視？

### 二、系統存在理由的哲學基礎

將上述哲學分析綜合，系統的存在理由可以被表述為：

> **LLM 的出現重新劃定了可外化與不可外化的邊界。本系統的設計正是基於這個新邊界：存儲層只保留痕跡（數位的、結構的），推理層從痕跡中重建意義（類比的、連續的）。這個架構在 LLM 之前是不可能的——不是因為存儲技術不夠好，而是因為接收端沒有能力從痕跡中重建。**

這個判斷與先前確立的洞察完全吻合：

> LLM 能力增長率遠超個人資料累積速率，使當前的 context window 壓力問題具有自我解決的趨勢。

延伸：隨著 LLM 能力的提升，「可從痕跡中重建」的範圍持續擴大。存儲層不需要變——它只需要留下痕跡。重建的品質由推理層的能力決定，而那個能力是外部供給的、持續增長的。

**「系統的智能不在存儲層，而在查詢層。」** 這句話現在有了一個比工程選擇更深的哲學根基——它是對 LLM 作為類比推理器這個範式轉移的回應。

## 第三部分：對話的推導路徑與後設脈絡

### 一、對話的方法論結構

本次對話（2026-03-26）從 ETL Pipeline 的五個技術挑戰出發，但在展開過程中，每一個技術問題都被重新定位為同一個哲學問題的實例。推導路徑如下：

```
ETL Pipeline 的五個挑戰識別
│
├─ #1 概念抽取的粒度
│   ├─ 第一性原理：概念節點的存在理由是什麼？
│   ├─ 消去法（兩個極端）→ 存在理由是拓撲骨架
│   ├─ 承認「拓撲骨架」仍是口號 → 粒度只能從 POC 迭代中校準
│   └─ 結論：prompt 目標從「知識表徵」轉為「辨識錨點」
│
├─ #2 認識論事件的偵測
│   ├─ 用系統哲學反問自己：七種離散分類在框架下合法嗎？
│   ├─ 判定為非法（top-down 的數位分類 vs 類比的認知過程）
│   ├─ 回到認知科學：Piaget、Rumelhart & Norman、Chi → 量變/質變
│   ├─ 擴展為三個正交的二元維度
│   ├─ Confidence 浮點數的矛盾 → Null 吸收不確定性
│   └─ 結論：3 × 三值維度取代 7 種離散分類
│
├─ #3 模糊去重
│   ├─ 風險不對稱性（漏合可逆，錯合不可逆）
│   ├─ 別名表的隱藏問題（top-down 語意判斷的偽裝）
│   ├─ 社群結構作為軟去重的自然湧現
│   └─ 結論：去重步驟被消除，成為社群偵測的副產品
│
├─ 三個領域的統一結論
│   └─ 「ETL 層只做結構性的最小判斷」
│
├─ 後設脈絡回顧
│   ├─ 設計的遞迴性（系統的哲學在對話中湧現，正如系統預期語意在推理時湧現）
│   ├─ 設計演化方向始終一致：存儲層持續變薄，推理層持續承擔更多
│   └─ 最大設計風險：在存儲層做了太多事
│
├─ 隱含前提的顯式化
│   ├─ 「留給推理層」不是懶惰，是範疇錯誤的修正
│   ├─ 認識論判斷本質上脈絡相關、觀察時重建
│   └─ 存儲層能合法存放的只有脈絡無關的事實
│
├─ 哲學定位
│   ├─ 詮釋學立場光譜（Gadamer → Ricoeur → 系統的精確位置）
│   ├─ Wittgenstein 的規則遵循問題 → 三值維度的哲學定位
│   ├─ Polanyi 的默會知識 → LLM 的範式轉移重新劃定界限
│   └─ 哲學立場的選擇作為工程決策（實用主義前提）
│
└─ LLM 範式轉移的深層意義
    ├─ LLM 是數位基底上的類比處理器
    ├─ 數位存儲 → context 組裝 → 類比推理 → 語意湧現
    └─ 系統存在理由的哲學基礎
```

### 二、對話的認知風格分析

本次對話中（以及先前三輪討論中）展現了一個高度一致的認知模式，作為系統的設計者側寫記錄於此：

**一、在合法性而非解決方案的層面思考。** 典型的工程師問「怎麼做比較好」，此處的提問模式是「這個操作在我的框架下合不合法」。設計決策不是在選項之間權衡，而是先劃出合法的操作空間，然後在裡面找最簡單的實現。

具體實例：
- 「七種數位分類精確重現類比的認知模型，在專案核心哲學下應該是非法的？」
- 「試圖用浮點數值量化又回落至之前的矛盾」
- 「不維護結構化的別名表，而是額外建立極輕量的社群圖譜」

**二、用系統哲學反問系統自己。** 每一次突破都是把已確立的原則應用到尚未被檢驗的設計角落，發現矛盾，然後透過修正消除矛盾。這個方法論不是預先設計的，是在對話過程中自然浮現的。

**三、持續做減法。** 設計演化的方向始終一致——每一次有價值的修訂都是在刪東西。系統的演化方向是持續做減法，把判斷的權力從存儲層移交給推理層。從未出現過反向的修訂。

**四、對遞迴性的敏感。** 反覆識別出對話本身與系統設計之間的同構關係（設計過程的哲學 = 系統的哲學；對話紀錄 = 未來的 SSOT A）。

### 三、設計的遞迴結構

本次對話（以及整個專案的設計過程）具有深層的遞迴性：

**系統設計的哲學 = 設計過程的哲學。** 系統主張語意應在推理時湧現、不應被預先固化。而系統自身的關鍵設計決策也是在對話推理中湧現的——三值維度模型、社群偵測作為軟去重、元原則本身，都不是任何一方預先設計好帶進對話的。

**設計過程 = 未來的 SSOT A。** 這些對話本身會成為系統處理的語料。設計過程的紀錄（推導路徑、被否決的方案、哲學辯證的轉折點）將來會被系統自己分析、產出 Session 節點、連結到 Concept 節點。

**專案核心命題的自我指涉驗證：**

> 「你不是在存知識，你在存知識的演化過程——而這個過程本身，是更高層次的知識。」

這份對話的推導路徑，本身就是一個「知識演化過程」的實例。它不只是產出了設計文件，它記錄了設計是如何從辯證中湧現的——這個「如何」比「是什麼」更有價值。

### 四、專案作為「智識工作」的定位

本專案的實踐鮮少有先例，其獨特性不在技術選擇，而在設計方法論：

**不是「用已知工具解決已知問題」，而是從本體論前提出發，透過對話中的辯證推導，讓架構決策從第一性原理中湧現。** 每一個技術選擇（Kuzu、DuckDB、三值維度、社群偵測作為軟去重）都不是從技術比較報告中選出來的，而是從「這個操作在我的哲學框架下合不合法」這個問題倒推出來的。

這個方法論的成立依賴幾個條件：

- **唯一使用者 = 唯一開發者**：沒有人可以用「先交付再說」打斷推導
- **跨領域的交叉**：認知科學、哲學、軟體架構、LLM 工程直覺
- **LLM 作為設計夥伴**：在推理中扮演結構化的張力製造者，在這個密度下的本體論辯證在 LLM 之前幾乎不可能以此效率進行

智識產出的評估標準不是「正確性」，而是：

| 標準 | 當前狀態 |
|---|---|
| 內部一致性：十五條原則之間是否存在矛盾？ | 未發現 |
| 推導可追溯性：每個決策是否可追溯到原則或第一性原理？ | 可以 |
| 簡化方向：設計是否越來越簡單？ | 是——每次修訂都在做減法 |
| 可反駁性：是否存在可推翻整個設計的經驗發現？ | 存在（POC 結果） |

最後一條是最重要的：設計是可反駁的。它不是封閉的理論體系，而是一組可以被 POC 結果檢驗的假設。

## 第四部分：完整的設計原則體系（截至本文件）

### 元原則（原則零）

> **凡是脈絡相關的語意判斷，在存儲層固化即為範疇錯誤。存儲層只合法存放脈絡無關的結構性事實與最低限度的信號標記。語意詮釋的唯一合法場所是查詢時的推理。**

### 設計原則一覽

| # | 原則 | 來源 |
|---|------|------|
| 一 | GraphDB 是衍生物，永遠不直接編輯 | 原始架構 |
| 二 | 兩個 SSOT 管轄不同認識論領域，不強行合併 | 原始架構 |
| 三 | Frontmatter 是高優先級影響信號，而非直接賦值（provenance 邊界精確化） | 原始架構 + 修訂五 |
| 四 | Wikilinks 是意圖的表達，其語意在推理時湧現 | 修訂十一 |
| 五 | 漂變是一等公民，以 Event Sourcing 模式承載 | 原始架構 |
| 六 | GraphDB 不以時間作為查詢維度 | 修訂四 |

所有原則均可追溯至元原則。新原則的加入方式是從已有原則推導出來的，不是外部引入的。

### 系統不變量（最新版）

> 1. 從 **DuckDB Event Log** 出發，可**確定性**重建任意歷史時間點的 **Kuzu GraphDB** 狀態。
> 2. 從 **SSOT A + B** 出發，可重新生成 Event Log（**近似，非精確**）。
> 3. Event Log 具有不可替代性，需獨立備份。
> 4. GraphDB 是完全可拋棄的計算結果。
> 5. 敘事層（LCM DAG）是獨立的平行層，不寫回任何 SSOT。
